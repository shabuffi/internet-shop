# 05. Заказы: от корзины до МойСклад

Бэкенд: [orders.py](../backend/app/api/v1/endpoints/orders.py), [tasks/sync.py](../backend/app/tasks/sync.py).
Фронтенд: [checkout/page.tsx](../frontend/src/app/checkout/page.tsx), [context/CartContext.tsx](../frontend/src/context/CartContext.tsx).
Модели: [order.py](../backend/app/db/models/order.py).

## Корзина живёт в браузере

Корзина — это React Context (`CartContext`), который хранит товары в `localStorage`
браузера. Сервер про корзину ничего не знает до момента оформления. Поэтому корзина
переживает перезагрузку страницы, но привязана к конкретному браузеру.

## Шаг 1: оформление заказа (фронтенд)

На `checkout/page.tsx` покупатель заполняет имя/телефон/адрес и жмёт «Подтвердить».
Форма шлёт POST на наш бэкенд:

```tsx
const res = await fetch("/api/v1/orders", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ ...form, items: items.map(i => ({ product_id: i.id, quantity: i.quantity })) }),
});
const order = await res.json();
clearCart();
router.push(`/checkout/success?order=${order.number}`);
```

Обрати внимание: с фронта едут только `product_id` и `quantity`. **Цену фронт не
присылает** — её бэкенд берёт из БД сам (чтобы нельзя было подделать цену из браузера).

## Шаг 2: создание заказа (бэкенд) — `create_order`

```python
@router.post("", response_model=OrderOut, status_code=201)
def create_order(payload: OrderIn, db):
    # 1. одним запросом подгружаем все товары
    products = {p.id: p for p in db.scalars(select(Product).where(Product.id.in_(product_ids)))}
    # 2. проверяем, что все существуют
    missing = [pid for pid in product_ids if pid not in products]
    if missing:
        raise HTTPException(422, f"Товары не найдены: {missing}")
    # 3. считаем сумму по ЦЕНАМ ИЗ БД и фиксируем их в позициях
    for item_in in payload.items:
        product = products[item_in.product_id]
        subtotal = product.price * item_in.quantity
        total += subtotal
        order_items.append(OrderItem(
            product_id=product.id, product_name=product.name,
            product_article=product.article, price=product.price, quantity=item_in.quantity,
        ))
    # 4. сохраняем заказ
    order = Order(number=_next_order_number(db), customer_name=..., total_amount=total, items=order_items)
    db.add(order); db.commit(); db.refresh(order)
    # 5. уведомление владельцу — ФОНОМ (заказ в МойСклад уезжает не отсюда, см. Шаг 3)
    notify_new_order.delay(order.id)
    return order
```

Ключевые моменты:
- Номер заказа `ORD-0001` — `_next_order_number` считает по количеству заказов в БД.
- `OrderItem` хранит **снимок** товара на момент заказа (имя, артикул, цену). Если
  потом товар в каталоге изменится — в заказе останется то, что было куплено.
- Заказ в МойСклад **не отправляется отсюда** — МойСклад забирает его сам через обмен
  (Шаг 3). Здесь только уведомление владельцу (мгновенно) + уже списанный остаток.
- Валидация телефона (минимум 10 цифр) и непустой корзины — в схеме
  [schemas/order.py](../backend/app/schemas/order.py) через `@field_validator`.

## Резерв остатка (анти-oversell)

Перед сохранением заказа бэкенд **атомарно списывает остаток** — чтобы двое не купили
последнюю единицу:

```python
for item_in in payload.items:
    result = db.execute(
        update(Product)
        .where(Product.id == item_in.product_id, Product.stock >= item_in.quantity)
        .values(stock=Product.stock - item_in.quantity)
    )
    if result.rowcount == 0:            # строк не обновилось → товара не хватает
        insufficient.append(item_in.product_id)

if insufficient:
    db.rollback()                        # откатываем уже списанные позиции
    raise HTTPException(409, detail={"message": "Недостаточно товара на складе", "items": [...]})
```

Почему именно так:
- **Условие `stock >= qty` внутри UPDATE** — проверка и списание происходят одной
  операцией БД. Если два заказа одновременно бьются за последнюю единицу, выиграет
  только один (у второго `rowcount == 0`). Обычная «проверил → списал» в две строки
  пропустила бы oversell в гонке.
- **Всё в одной транзакции** со вставкой заказа: либо списали остаток И создали заказ,
  либо `rollback` и ничего. Если не хватило хотя бы одной позиции — отклоняется весь
  заказ (корзина = всё-или-ничего).
- Ответ **409** содержит `items` со списком товаров и доступным количеством — фронт на
  чекауте показывает покупателю понятное «Недостаточно товара: …».
- На витрине кнопка «В корзину» при `stock == 0` заменяется на «Нет в наличии», а
  степпер на карточке товара не даёт выбрать больше, чем есть. Бэкенд (409) — страховка.

⚠️ МойСклад остаётся **мастером остатка**: при следующем обмене `offers.xml` перезапишет
`stock` своим значением (с учётом резерва, который МойСклад создаёт при импорте заказа).
Локальное списание — это «мост» между обменами, чтобы не пере-продать до синхронизации.

## Шаг 3: МойСклад забирает заказ через обмен CommerceML

Заказы уходят **не** через REST — МойСклад **сам забирает** их у магазина по обмену
(pull-модель). Никакого пароля аккаунта не нужно, только пара обмена. Реализация — в
[exchange.py](../backend/app/api/v1/endpoints/exchange.py), сериализация — в
[commerceml_orders.py](../backend/app/integrations/moysklad/commerceml_orders.py).

Протокол (МойСклад → магазин, `type=sale`):
1. `GET ?type=sale&mode=checkauth` / `mode=init` — авторизация (как для каталога).
2. `GET ?type=sale&mode=query` → отдаём **неэкспортированные** заказы (`exported_at IS NULL`,
   `status != cancelled`) как CommerceML-XML (`build_orders_xml`). id заказов запоминаем в Redis.
3. `GET ?type=sale&mode=success` → помечаем эти заказы `exported_at = now`.

Что в XML заказа:
- **Контрагент**: имя (полное «Имя Фамилия»), телефон, email — МойСклад сам создаёт/находит
  контрагента по этим данным.
- **Товары**: по `<Ид>` = `Product.moysklad_id` (id из выгрузки каталога; Коды связи —
  «уникальные для магазина»). Поиск по артикулу/REST не нужен.
- **Реквизиты**: адрес доставки, комментарий клиента.

Что делает сам МойСклад при импорте:
- **Создаёт контрагента** (по имени/телефону/email).
- **Резервирует товар** — если в настройках обмена включено «Резервировать товары».
  Тогда «Доступно» падает, и следующая выгрузка остатков приносит на сайт корректное число.

Особенности:
- **Без дублей**: повторно заказ не уходит (после `mode=success` стоит `exported_at`).
- **Задержка**: МойСклад забирает по расписанию (например, раз в 1–5 мин) — не мгновенно.
  Мгновенно работают только уведомление владельцу и списание остатка на сайте.
- **Статус выгрузки** в админке (Заказы → колонка «Выгрузка»): `Ожидает` / `Выгружен`
  по полю `exported_at`.

## Управление статусом заказа (админка)

Статусы: `new → confirmed → shipped → delivered / cancelled` (поле `Order.status`).

Бэкенд — [admin.py](../backend/app/api/v1/endpoints/admin.py):

```python
class OrderStatusUpdate(BaseModel):
    status: Literal["new", "confirmed", "shipped", "delivered", "cancelled"]

@router.patch("/orders/{order_id}/status")
def update_order_status(order_id, body: OrderStatusUpdate, db, _=Depends(_get_current_admin)):
    order = db.get(Order, order_id)
    if not order:
        raise HTTPException(404, "Заказ не найден")
    order.status = body.status
    db.commit()
    return {"id": order.id, "status": order.status}
```

Pydantic с `Literal` сам валидирует статус — недопустимое значение даёт 422 ещё до
тела функции. Требует JWT админа (`_get_current_admin`).

**Отмена заказа возвращает остаток на сайт.** При переходе в `cancelled` (если заказ ещё
не был отменён) `update_order_status` делает атомарный инкремент `stock += quantity` по
каждой позиции. Проверка «был ли уже отменён» защищает от двойного возврата. Резерв в
МойСклад снимается на стороне МойСклад (проброс отмены заказа в МойСклад — отдельная
доработка статусов; пока при отмене резерв там убирают вручную).

Фронтенд — [admin/orders/page.tsx](../frontend/src/app/admin/orders/page.tsx): в каждой
строке таблицы `<select>` со статусами. При смене — **оптимистичное** обновление
(меняем в UI сразу), а если запрос упал — перечитываем список с сервера (источник
правды) и показываем ошибку.

## Уведомление о новом заказе

При создании заказа `create_order` ставит в очередь фоновую задачу уведомления владельцу
— `notify_new_order` ([tasks/notify.py](../backend/app/tasks/notify.py)). Это **единственная**
фоновая задача (в МойСклад заказ уезжает обменом, отдельной отправки нет).

Каналы — **Telegram и ВКонтакте**, независимые. Задача шлёт в каждый, что настроен
(задан токен и адресат); если ни один — просто пишет в лог. Ошибки отправки не
пробрасываются — уведомление не должно ронять заказ. Логика отправки в
[integrations/notify.py](../backend/app/integrations/notify.py):
`build_order_message` собирает текст (номер, покупатель, позиции, итог), `send_telegram`
(Bot API) и `send_vk` (`messages.send` от имени сообщества) — отправляют.

Креды берутся из `ShopSettings` (админка → Настройки → «Уведомления о заказах») с
фолбэком на `.env`. Токены хранятся открытым текстом (они исходящие) и маскируются в
выдаче `GET /settings` как `***`.

- **Telegram:** бот у @BotFather → `token`; `chat_id` — id владельца (узнать через
  @userinfobot или `getUpdates`).
- **ВК:** ключ доступа сообщества; писать можно только тому, кто **сам написал
  сообществу первым** — поэтому владелец пишет сообществу, а `peer_id` — его id ВК.
