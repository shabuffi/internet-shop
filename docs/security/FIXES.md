## Stage 3 — 2026-07-14 (в коде + 2 миграции, НЕ задеплоено)

- **B-1** Номер заказа — race-free через Postgres SEQUENCE.
  - Миграция `d5e6f7a8b9c0_add_order_number_sequence.py`: `CREATE SEQUENCE order_number_seq`, `setval` = максимальный существующий номер (nextval стартует с max+1, без пересечения).
  - `orders.py` `_next_order_number` теперь `SELECT nextval('order_number_seq')` → `ORD-{n:04d}` (было `COUNT(*)+1`). Импорт `func`→`text`.
  - Почему устранено: `nextval` атомарен и не блокирует; при нескольких воркерах/параллельных запросах номера не дублируются (раньше два одновременных заказа брали одинаковый `COUNT+1` → второй падал на unique-constraint 500). Возможны пропуски при откате — номерам нужна только уникальность.
  - Проверка: `nextval` дважды → 16, 17 (последовательно, атомарно); `_next_order_number` → `ORD-0016`/`ORD-0017`; sequence возвращён на 15 (следующий реальный заказ = ORD-0016). Backend reload чистый, `/health` 200.

- **B-2** Уникальность `users.phone` на уровне БД.
  - Модель `db/models/user.py`: `phone` → `unique=True, index=True` (было без ограничения).
  - Миграция `d6e7f8a9b0c1_unique_user_phone.py`: гард — если есть дубли телефонов, миграция ОСТАНАВЛИВАЕТСЯ с сообщением и НЕ удаляет записи; иначе `CREATE UNIQUE INDEX ix_users_phone`.
  - Почему устранено: устраняет TOCTOU-гонку (две одновременные регистрации с одним телефоном проходили проверку в коде и создавали 2 аккаунта); теперь второй INSERT отклоняется БД.
  - Проверка: локально дублей нет (12 юзеров) → миграция прошла; unique-индекс создан; попытка вставить дубль телефона → `duplicate key ... ix_users_phone` (в откаченной транзакции, данные не изменены).
  - ⚠️ **Перед деплоем на прод** проверить дубли: `SELECT phone, COUNT(*) FROM users GROUP BY phone HAVING COUNT(*)>1;` — если есть, миграция намеренно упадёт (устранить вручную, записи не удаляются автоматически).

## Смена email покупателя — 2026-08-03 (в коде + 1 миграция, НЕ задеплоено)

Email в проекте — логин, поэтому смена сделана двухшаговой; попутно закрыт B-3.

- **Модель/миграция** `db/models/user.py`, `migrations/versions/b3c4d5e6f7a8_add_user_pending_email.py` — колонки `pending_email`, `pending_email_at` (обе nullable, существующие покупатели не затронуты). Unique-индекса на `pending_email` намеренно НЕТ: два клиента вправе заявить один адрес, побеждает первый подтвердивший.
- **Заявка** `POST /auth/change-email` (`auth.py`) — требует **текущий пароль** (иначе украденной куки хватило бы для захвата аккаунта через последующее «восстановление пароля»), проверяет занятость (409), кладёт адрес в `pending_email`. `users.email` на этом шаге НЕ меняется: вход остаётся по старому адресу.
- **Подтверждение** `POST /auth/change-email/confirm` — публичное (письмо открывают в другом браузере), авторизует сам JWT: `typ=emailchange`, срок 24 ч, отпечаток текущего email + сверка `token["new"] == user.pending_email`. Одноразовость — по образцу токена сброса пароля (`_pw_fingerprint`), без таблицы токенов: после подтверждения/отмены заявки в БД нет → ссылка мертва. Новая заявка обесценивает старую ссылку.
- **Гонка уникальности:** повторная проверка занятости при подтверждении + `try/except IntegrityError` → 409 (не 500). Тот же гард добавлен в `register` (**B-3**).
- **Отмена** `POST /auth/change-email/cancel` — снимает заявку, ссылка из письма перестаёт работать.
- **Rate-limit:** заявка 10/ч по IP + **5/ч по аккаунту** (чтобы форму нельзя было превратить в рассыльщик писем на чужие адреса), подтверждение 20/ч, `check-email` 120/ч.
- **Письма** `tasks/notify.py` — `send_email_change_confirm` (на НОВЫЙ адрес, ссылка `/email-confirm?token=…`) и `notify_email_changed` (на СТАРЫЙ адрес: единственный канал, по которому владелец узнает о подмене). Сбой очереди не роняет запрос — как в регистрации.
- **Подсказка об опечатках** `services/email_typos.py` + `POST /auth/check-email` — регистрацию НЕ блокирует; словарь живёт только на бэкенде (фронт спрашивает по API, копии в TS нет). Занятость адреса этот публичный эндпоинт не проверяет намеренно — иначе он позволял бы перебирать зарегистрированные адреса.
- **Фронт:** `components/EmailTypoHint.tsx` (общий для регистрации и ЛК), блок «Email для входа» в ЛК (текущий адрес, плашка «ожидает подтверждения», отмена), страница `/email-confirm`.

Проверка: **230 тестов зелёные** (новые — `tests/test_email_change.py` 19 шт., `tests/test_email_typos.py` 36 шт.), `tsc --noEmit` чист, alembic head единый (`b3c4d5e6f7a8`). Снимок `orders.customer_email` намеренно не переписывается — история заказов и выгрузка в МойСклад остаются как на момент заказа; `id` и `moysklad_ext_code` при смене не меняются (покрыто тестом).
