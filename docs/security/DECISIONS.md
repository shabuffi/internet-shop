# Security Decisions

**Назначение.** Этот файл — история архитектурных и security-решений проекта. Он объясняет **почему** было выбрано то или иное решение и **почему отвергнуты** альтернативы. Это «журнал рассуждений», дополняющий остальные документы фактами о мотивации.

**Как обновлять.**
- После каждого архитектурного или security-изменения добавляй новую запись **в конец** файла.
- Не переписывай документ целиком.
- Если ранее принятое решение изменилось — **обновляй существующую запись** (добавляй подраздел «Обновление YYYY-MM-DD»), а не создавай дубликат.
- Всегда описывай не только итог, но и рассмотренные варианты с плюсами/минусами.
- Ставь дату в заголовке записи.

**Что сюда НЕ записывать.**
- Список находок и их статусы → `AUDIT.md`.
- Технику каждого фикса (файлы, строки, как проверено) → `FIXES.md`.
- Оставшиеся задачи → `TODO.md`.
- Хронологию событий → `CHANGELOG.md`.
- Сюда — только **мотивация выбора** между вариантами.

## 2026-07-14 — CommerceML-обмен: fail-open → fail-closed

### Проблема
Эндпоинт обмена `/api/v1/1c/exchange` при отсутствии заданной пары логин/пароль обмена в админке пускал **любой** запрос без аутентификации («мягкий режим»). В этом состоянии `mode=query` отдаёт заказы с ПДн, а `mode=import` перезаписывает каталог. Дефолт был небезопасным.

### Рассмотренные варианты
1. **Оставить fail-open, добавить алерт при пустых кредах.**
   - Плюсы: не ломает уже настроенный обмен; ноль изменений поведения.
   - Минусы: окно полной открытости сохраняется (свежий деплой, ручная очистка поля); защита — только внешний мониторинг.
2. **Fail-closed: без кредов эндпоинт недоступен.** (выбран)
   - Плюсы: безопасный дефолт; невозможно случайно оставить обмен открытым.
   - Минусы: на новом деплое обмен не работает, пока креды не заданы (нужен явный шаг настройки).
3. **Автогенерация кредов из env при старте.**
   - Плюсы: закрыто по умолчанию + меньше ручных шагов.
   - Минусы: новая точка хранения секрета, усложнение конфигурации, отход от «пара задаётся в админке» — изменение архитектуры.

### Принятое решение
Вариант 2. `_is_authorized` возвращает `False` при пустых кредах; ветка `checkauth` отдаёт `failure` вместо статичной сессии.

### Почему именно оно
На проде креды уже заданы (проверено), поэтому реального изменения поведения нет, а латентный риск «однажды открыто всем» устраняется полностью. Вариант 1 оставляет саму дыру. Вариант 3 меняет модель хранения секрета — избыточно для устранения одной проблемы, противоречит требованию «не менять архитектуру».

### Последствия
Настроенный обмен работает как прежде. **Ограничение/компромисс:** на чистой установке обмен МойСклад не заработает до задания пары логин/пароль в админке — это осознанный trade-off (безопасный дефолт важнее «заработало сразу»).

### Связанные файлы
- `backend/app/api/v1/endpoints/exchange.py`

### Связанные документы
- AUDIT.md (H-1), FIXES.md (Stage 1)

## 2026-07-14 — Swagger/OpenAPI/Redoc только при DEBUG

### Проблема
Интерактивная документация (`/docs`, `/redoc`, `/openapi.json`) была доступна на проде, раскрывая всю карту API (включая `/admin/*`, `/1c/exchange`, `/dev/*`) и упрощая разведку.

### Рассмотренные варианты
1. **Закрыть доступ на уровне nginx (убрать `location /docs`, `/openapi.json`).**
   - Плюсы: не трогает код.
   - Минусы: два источника правды (nginx на проде vs код); при прямом доступе к backend (в обход nginx) docs снова открыты; легко забыть при смене конфигурации.
2. **Гейт в приложении по `settings.DEBUG`.** (выбран)
   - Плюсы: авторитетно на уровне приложения независимо от прокси; один флаг; локальная разработка сохраняет docs.
   - Минусы: небольшая логика в `main.py`.
3. **Прятать за авторизацией (basic-auth на /docs).**
   - Плюсы: docs доступны админам на проде.
   - Минусы: лишний механизм и секрет; на проде docs не нужны в принципе — избыточно.

### Принятое решение
Вариант 2. `docs_url`/`redoc_url`/`openapi_url` = `None`, когда `not settings.DEBUG`.

### Почему именно оно
Гейт в приложении закрывает и путь в обход nginx, и остаётся верным при любой конфигурации прокси. Вариант 1 оставляет обходной путь и раздваивает конфигурацию. Вариант 3 добавляет ненужную на проде функциональность.

### Последствия
На проде (`DEBUG=false`) docs/openapi отдают 404; в разработке (`DEBUG=true`) — работают. **Компромисс:** для отладки схемы на проде нужно временно включить DEBUG (не рекомендуется) — приемлемо, т.к. схему смотрят локально.

### Связанные файлы
- `backend/app/main.py` (nginx оставлен как есть — просто проксирует и получает 404)

### Связанные документы
- AUDIT.md (H-2), FIXES.md (Stage 1)

## 2026-07-14 — Security Headers в nginx

### Проблема
Прод-nginx не отдавал security-заголовков: нет HSTS, защиты от clickjacking (`X-Frame-Options`), `X-Content-Type-Options`, `Referrer-Policy`, CSP.

### Рассмотренные варианты
1. **Полный набор заголовков вместе со строгой CSP.**
   - Плюсы: максимальная защита, включая XSS-mitigation через CSP.
   - Минусы: строгая CSP почти наверняка сломает Next.js (inline-стили темы через `dangerouslySetInnerHTML`, внешние шрифты Google) — высокий риск регресса витрины.
2. **Безопасный минимум без CSP: HSTS + X-Frame-Options + nosniff + Referrer-Policy.** (выбран)
   - Плюсы: закрывает clickjacking/HSTS/MIME-sniffing без риска сломать фронт; можно катить сразу.
   - Минусы: нет CSP-защиты от инъекций (частично компенсируется тем, что XSS в проекте не найдено).
3. **CSP в режиме `Report-Only`.**
   - Плюсы: наблюдение за нарушениями без блокировки.
   - Минусы: нужен endpoint сбора отчётов и итерации; отложено на будущее.

### Принятое решение
Вариант 2. Четыре заголовка на уровне `server` блока 443 с флагом `always`.

### Почему именно оно
Прямое требование заказчика — не добавлять слишком строгую CSP, способную сломать фронт. Минимальный набор даёт основную защиту (в первую очередь anti-clickjacking для `/admin` и `/account`) без риска регресса. CSP оставлена на будущее (вариант 3) как отдельный шаг.

### Последствия
Появляются security-заголовки на всех ответах прод-домена. **Ограничение:** нет CSP → инъекционная защита слабее (приемлемо: XSS не обнаружено, тема валидируется regex, контент экранируется React). Заголовки на уровне `server`; ни одна `location` не использует свой `add_header`, поэтому перекрытия нет.

### Связанные файлы
- `nginx/nginx.prod.conf`

### Связанные документы
- AUDIT.md (H-3), FIXES.md (Stage 1), TODO.md (CSP — на будущее)

## 2026-07-14 — Rate limiting для /orders и /leads

### Проблема
Публичные POST `/orders` и `/leads` не имели ограничения частоты → возможен спам заказами/заявками: флуд уведомлений владельцу, рост БД, письма на произвольные адреса.

### Рассмотренные варианты
1. **Переиспользовать существующий `rate_limit()` (Redis, скользящее окно).** (выбран)
   - Плюсы: механизм уже есть и применяется на auth-эндпоинтах; ноль новых зависимостей; единый подход; fail-open при недоступности Redis.
   - Минусы: лимит по IP (за прокси — по `X-Forwarded-For`), грубоват при NAT.
2. **Ввести отдельную библиотеку/middleware (например slowapi).**
   - Плюсы: больше возможностей (глобальные лимиты, декораторы).
   - Минусы: новая зависимость, изменение архитектуры — противоречит ограничениям задачи.
3. **Лимитировать на уровне nginx (`limit_req`).**
   - Плюсы: отсекает нагрузку до приложения.
   - Минусы: конфиг размазан между слоями; сложнее выставлять доменную логику (разные лимиты на разные ручки); дублирует уже готовый механизм приложения.

### Принятое решение
Вариант 1. `rate_limit(f"rl:order|lead:{client_ip}", limit=10, window_sec=600)` в начале обработчиков.

### Почему именно оно
Использование готового механизма — минимальное изменение без новых зависимостей и без смены архитектуры (прямое требование). Лимит 10/10 мин щедрый для реальных пользователей и режет только флуд. Варианты 2/3 добавляют слои/зависимости ради задачи, которую закрывает существующий код.

### Последствия
Спам-флуд отсекается 429. **Компромисс:** fail-open (если Redis недоступен — не блокируем) — сознательный выбор: доступность оформления заказа важнее строгого лимита. Лимит по IP может задеть пользователей за общим NAT (10/10 мин — с запасом, риск мал).

### Связанные файлы
- `backend/app/api/v1/endpoints/orders.py`, `backend/app/api/v1/endpoints/leads.py`

### Связанные документы
- AUDIT.md (M-2), FIXES.md (Stage 1)

## 2026-07-14 — Защита /admin/setup через SETUP_TOKEN (не DEBUG)

### Проблема
`POST /admin/setup` создавал первого администратора без аутентификации (защита — только «админ уже существует»). На пустой/сброшенной БД любой мог создать админа.

### Рассмотренные варианты
1. **Гейт по `settings.DEBUG` (первая итерация).**
   - Плюсы: просто; на проде закрыто.
   - Минусы: привязка безопасности к режиму отладки — плохая практика; первичный bootstrap на чистом проде становится невозможен без включения DEBUG. Заказчик прямо отверг этот подход.
2. **Одноразовый `SETUP_TOKEN` из конфигурации.** (выбран)
   - Плюсы: не зависит от DEBUG; явный, отзываемый механизм; работает и на чистом проде (задать токен на время установки, потом убрать); constant-time сравнение.
   - Минусы: нужен новый параметр конфигурации; оператор должен не забыть убрать токен после установки.
3. **Убрать эндпоинт, создавать админа CLI-скриптом/миграцией.**
   - Плюсы: нет публичной ручки вообще.
   - Минусы: меняет процесс развёртывания; менее удобно; отдельный код для bootstrap.

### Принятое решение
Вариант 2. Требуются одновременно: задан `settings.SETUP_TOKEN` (пусто → 403), верный токен в теле `setup_token` или заголовке `X-Setup-Token` (сравнение `hmac.compare_digest`, иначе 401), и отсутствие уже созданного админа (иначе 400).

### Почему именно оно
Прямое требование заказчика — не использовать DEBUG как механизм защиты и завязать доступ на одноразовый токен. Порядок проверок (сначала токен, потом наличие админа) не раскрывает существование админа без валидного токена. Вариант 1 отвергнут заказчиком; вариант 3 меняет процесс развёртывания сильнее необходимого.

### Последствия
Эндпоинт по умолчанию закрыт наглухо (403). **Компромисс:** для первичной установки на проде нужно временно задать `SETUP_TOKEN` в окружении и убрать после создания админа — задокументировано в конфиге.

### Связанные файлы
- `backend/app/api/v1/endpoints/admin.py`, `backend/app/core/config.py` (поле `SETUP_TOKEN`)

### Связанные документы
- AUDIT.md (M-5), FIXES.md (Stage 1)

## 2026-07-14 — Номера заказов через PostgreSQL Sequence (вместо COUNT(*))

### Проблема
Номер заказа вычислялся как `COUNT(*)+1`. При нескольких воркерах два одновременных заказа получали одинаковый номер; т.к. `orders.number` — `unique`, второй `INSERT` падал с 500 (race condition).

### Рассмотренные варианты
1. **Блокировка в приложении (mutex/advisory lock вокруг генерации).**
   - Плюсы: минимальная схема БД.
   - Минусы: application-lock прямо запрещён требованием; сериализует заказы; хрупко при нескольких процессах.
2. **`SELECT ... FOR UPDATE` / пересчёт в транзакции с блокировкой строки.**
   - Плюсы: без новых объектов БД.
   - Минусы: блокировки на горячем пути; сложнее; всё ещё уязвимо к гонкам при неверной изоляции.
3. **Postgres SEQUENCE + `nextval`.** (выбран)
   - Плюсы: атомарно и без блокировок по определению; безопасно при любом числе воркеров; штатный механизм БД.
   - Минусы: возможны пропуски в нумерации при откате транзакции (нумерация не сплошная).
4. **UUID/случайный номер вместо ORD-XXXX.**
   - Плюсы: тривиально уникален.
   - Минусы: ломает человекочитаемый формат `ORD-0001`, к которому привязаны админка/письма/выгрузка — изменение поведения.

### Принятое решение
Вариант 3. Миграция создаёт `order_number_seq` (стартовое значение = максимальный существующий номер), `_next_order_number` использует `nextval`.

### Почему именно оно
Sequence — каноничный race-free-механизм, прямо разрешённый требованием («если нужна последовательность — используй её»), и явный запрет на application-lock исключает варианты 1–2. Формат `ORD-XXXX` сохранён (вариант 4 его ломает).

### Последствия
Параллельные заказы получают уникальные номера без 500. **Компромисс:** нумерация может иметь пропуски при откатах — приемлемо, номерам нужна только уникальность, а не непрерывность. Требуется миграция БД.

### Обновление 2026-07-14 (финальный review)
Тестовая БД — SQLite in-memory, где `nextval`/sequence не поддерживаются → первый прогон тестов упал (`no such function: nextval`). Решение: `_next_order_number` сделан **dialect-aware** — на `postgresql` используется `nextval` (боевой race-free путь), на прочих диалектах (только тесты) — фолбэк `MAX(number)+1`. Прод всегда на Postgres, поэтому боевая гарантия не ослаблена; фолбэк существует исключительно для тестового окружения.

### Связанные файлы
- `backend/migrations/versions/d5e6f7a8b9c0_add_order_number_sequence.py`, `backend/app/api/v1/endpoints/orders.py`

### Связанные документы
- AUDIT.md (B-1), FIXES.md (Stage 3), CHANGELOG.md

## 2026-07-14 — Уникальность телефона через ограничение БД

### Проблема
`users.phone` проверялся на уникальность только в коде регистрации → TOCTOU-гонка: две одновременные регистрации с одним номером создавали два аккаунта («один номер = один аккаунт» нарушался).

### Рассмотренные варианты
1. **Оставить проверку только в коде, обернуть в транзакцию/лок.**
   - Плюсы: без миграции.
   - Минусы: не устраняет гонку надёжно; логика на приложении вместо гаранта БД.
2. **Уникальный индекс на уровне БД + миграция.** (выбран)
   - Плюсы: БД — надёжный арбитр; гонка невозможна; симметрично с `email` (уже `unique`).
   - Минусы: миграция упадёт, если в данных уже есть дубли телефонов.
3. **Уникальный индекс + автоматическое слияние/удаление дублей в миграции.**
   - Плюсы: миграция «пройдёт всегда».
   - Минусы: автоматическое удаление данных опасно и прямо запрещено требованием.

### Принятое решение
Вариант 2 с защитным гардом: миграция сперва ищет дубли и при их наличии **останавливается с понятным сообщением, ничего не удаляя**; иначе создаёт `UNIQUE INDEX ix_users_phone`. Модель: `phone` → `unique=True, index=True`.

### Почему именно оно
Ограничение на уровне БД — единственный надёжный способ против TOCTOU. Автоудаление дублей (вариант 3) запрещено требованием и рискованно, поэтому выбран безопасный гард: решение о дублях принимает человек. Локально дублей нет — миграция прошла.

### Последствия
Второй аккаунт с тем же телефоном отклоняется БД. **Ограничение/компромисс:** перед деплоем на прод нужно вручную проверить и устранить возможные дубли (`SELECT phone, COUNT(*) FROM users GROUP BY phone HAVING COUNT(*)>1`) — иначе миграция намеренно не применится. Данные не удаляются автоматически.

### Связанные файлы
- `backend/app/db/models/user.py`, `backend/migrations/versions/d6e7f8a9b0c1_unique_user_phone.py`

### Связанные документы
- AUDIT.md (B-2), FIXES.md (Stage 3), CHANGELOG.md

## 2026-07-14 — Ведение документации по безопасности (docs/security/)

### Проблема
Результаты аудита и исправления фиксировались только в переписке. Нужен постоянный, версионируемый источник правды по безопасности, живущий вместе с кодом.

### Рассмотренные варианты
1. **Хранить в памяти агента / внешнем трекере.**
   - Плюсы: не засоряет репозиторий.
   - Минусы: не версионируется с кодом, не виден в PR, теряется контекст «почему».
2. **Единый файл SECURITY.md.**
   - Плюсы: просто.
   - Минусы: смешивает находки, фиксы, задачи и мотивацию — быстро становится нечитаемым.
3. **Каталог `docs/security/` с разделением ответственности.** (выбран)
   - Плюсы: каждый файл — своя роль (AUDIT/FIXES/TODO/CHANGELOG/DECISIONS); инкрементальное обновление; видно в git.
   - Минусы: несколько файлов надо держать в синхронизации.

### Принятое решение
Вариант 3. Пять документов: `AUDIT.md` (реестр находок), `FIXES.md` (техника фиксов), `TODO.md` (осталось), `CHANGELOG.md` (хронология), `DECISIONS.md` (мотивация). Обновляются инкрементально, с датой; правило закреплено в `CLAUDE.md`.

### Почему именно оно
Разделение по ролям исключает дублирование и делает каждый документ читаемым и обновляемым точечно. Хранение в репо даёт версионирование и видимость в ревью. Единый файл (вариант 2) не масштабируется.

### Последствия
Появился постоянный источник правды по безопасности. **Компромисс:** дисциплина синхронизации нескольких файлов — снимается правилом в `CLAUDE.md` (обновлять все документы после каждого этапа перед показом результатов).
