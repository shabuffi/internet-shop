## Спринт 6 — Поиск при неправильной раскладке + фикс прод-сборки · 2026-06-21

**Готово:**
- Характеристики из **свойств** МойСклад (`commerceml_parser.py`): по реальному import.xml выяснилось,
  что описания/характеристики/модификации НЕ заполнены — есть только технические реквизиты и
  свойства-сертификаты. Парсер раньше читал лишь реквизиты; добавлены `_parse_properties` (карта
  Ид→название из `<Классификатор><Свойства>`) и `_property_values` (значения из `<ЗначенияСвойств>`,
  МойСклад использует нестандартный элемент `<ЗначенияСвойства>`). Проверено на реальном обмене:
  4788 товаров получили характеристику (сейчас — «Орган, выдавший сертификат»). Реальные
  характеристики (вес/цвет/состав) появятся, когда их заполнят свойствами в МойСклад.
- Диагностика данных МойСклад (по `exchange:diag:import.xml`): 12 513 товаров, описаний 0,
  `ХарактеристикиТовара` 0, артикулов ~6% (остальные `<Артикул></Артикул>`), картинок в import 0.
- `backend/app/api/v1/endpoints/products.py` — поиск учитывает раскладку: `_layout_variants()`
  даёт исходный запрос + EN→RU + RU→EN, ищем по всем (`or_`). Проверено: `vskj`→«мыло» (207=207),
  `yjcrb`→«носки» (198=198).
- `frontend/.dockerignore` (фикс прод-падения): без него `COPY . .` тащил локальный `.next` в
  сборку → прод-build наслаивался на устаревший → рантайм `Cannot find module './XX.js'`.
  Исключили `.next/node_modules/логи`. Лечение на сервере: `rm -rf frontend/.next` +
  `build --no-cache frontend`.

## Спринт 5 — Характеристики товара (плумбинг) + вид карточки · 2026-06-21

**Контекст:** ТЗ хочет характеристики из МойСклад в карточке. ВАЖНАЯ находка по реальной БД
(12 510 товаров): данные в МойСклад почти не заполнены — описания 0%, фото 1%, артикулы 6%,
цена 99.9%. Парсер работает; проблема — наполнение каталога на стороне МойСклад. Характеристик
поэтому пока нет; сделан плумбинг, чтобы они появились автоматически, когда их заполнят.

**Готово (локально, ждёт деплоя):**
- Парсер `commerceml_parser.py`: `ParsedProduct.attributes` — реквизиты товара (`ЗначениеРеквизита`),
  кроме технических/уже используемых (`_NON_ATTR_REQS`: Описание, Артикул, Код, ТипНоменклатуры…).
  Проверено синтетическим import.xml: «Вес»/«Цвет» извлекаются, «Описание»/«ТипНоменклатуры» — нет.
- Модель `db/models/product.py`: колонка `attributes` (JSON). Миграция
  `c9d0e1f2a3b4_add_product_attributes.py` (применена локально).
- `import_service.py`: маппинг attributes (create — всегда; update — только если пришли).
- Схема `ProductOut`: поле `attributes: list[dict]`. API отдаёт его (сейчас null — данных нет).
- Фронт: `types/product.ts` (тип `attributes`); карточка `products/[id]/page.tsx` переоформлена в
  стиле маркетплейса (Сима-ленд, без отзывов): галерея | цена+кнопка сразу под ценой → «Описание»
  (только если есть) → единый блок «Характеристики» (модификации МойСклад + артикул/категория/
  остаток/наличие). CSS `.pdp__specs`: длинные значения (состав и т.п.) переносятся.
- `migrations/env.py`: зарегистрирована модель `lead` для Alembic.

**Открытый вопрос:** наполнить МойСклад (описания/фото/характеристики) — это на стороне заказчика.
Без данных карточка остаётся минималистичной (имя/цена/остаток). Можно проверить плумбинг «вживую»,
заполнив 1–2 товара в МойСклад и прогнав обмен.

## Спринт 3 — Карта зоны доставки на главной · 2026-06-21

**Контекст:** ТЗ — «вместо пустого синего пространства справа в баннере разместить карту России
с регионами доставки». Регионов по факту **6** (не 8): Тверская, Московская, Смоленская,
Новгородская, Владимирская, Ярославская.

**Готово (локально, ждёт деплоя):**
- `frontend/src/components/DeliveryMap.tsx` — НАСТОЯЩАЯ карта 6 областей с точными границами.
  Контуры построены из OSM-GeoJSON (репозиторий timurkanaz/Russia_geojson_OSM): районы каждой
  области объединены (shapely unary_union), спроецированы (коррекция долготы по cos(ср.широты)),
  упрощены (simplify 0.01°), переведены в SVG-пути (viewBox 920×748). Москва-город влит в
  Московскую область (иначе МО — «подкова» с дыркой и выглядела маленькой). Дырки залиты;
  под областями подложка-union, закрывающая тонкие щели между независимо упрощёнными
  границами. Ховер-подсветка на CSS, без клиентского JS.
- `frontend/src/app/page.tsx` — hero перестроен в 2 колонки (текст слева, карта справа, скрыта на
  мобильных через `hide-mobile`); список регионов в блоке «Доставка» расширен до 6.

**Как пересобрать карту (если поменяется список регионов):** скачать нужные GeoJSON из
timurkanaz/Russia_geojson_OSM (папки Regions/CFO, SZFO), прогнать через shapely (union→project→
simplify) и сгенерировать пути. shapely ставился разово ЛОКАЛЬНО для генерации — в зависимости
проекта НЕ входит; в рантайме карта это статический SVG.

**Проверки:** `tsc` = 0; главная 200; карта и 6 регионов в разметке.

## Спринт 2 — Этап 1 доработок по ТЗ заказчика · 2026-06-21

**Контекст:** заказчик прислал ТЗ на модернизацию витрины. Этап 1 — три блока (главная-контент,
«О компании», категории+фильтрация) + минимальный заказ. Остальное (карта России, характеристики
из МойСклад, поиск по раскладке, общий редизайн) — следующие этапы.

**Готово (локально проверено, ждёт деплоя):**
- **Главная — контент** (`frontend/src/app/page.tsx`): убраны блоки «4 области» и «−10% на первый
  заказ»; добавлены «24/7» и «от 5 000 ₽» в полосу доверия; переписан hero; **удалены обе формы
  «Получить прайс» (LeadForm)** по решению владельца.
- **8 категорий-плиток → конкретный раздел каталога** (`page.tsx`): плитки Бытовая химия, Хозтовары,
  Сад и дача, Игрушки, Канцтовары, Обувь, Носки, Бижутерия. Ссылка строится в рантайме:
  `getCategories()` → толерантный матч имени (точное → startsWith → includes) → `/catalog?category_id=…`;
  если категория не нашлась — fallback `/catalog?search=…`. Плитки увеличены (картинка 120px, карточки шире).
- **Картинки категорий**: нарезаны из присланного `8 продуктов.png` (1536×1024, сетка 4×2) скриптом PIL
  (композит на белом фоне → автокроп по насыщенным пикселям) в `frontend/public/categories/cat-*.png`.
  Имена файлов = id плитки (`cat-chem`, `cat-home`, `cat-garden`, `cat-toys`, `cat-stationery`,
  `cat-shoes`, `cat-socks`, `cat-jewelry`).
- **«О компании»** (`frontend/src/app/about/page.tsx`): официальный текст ТЗ (с 2016, ежедневные
  поступления, индивидуальный подход, «Спасибо, что Вы с нами!»). Блок реквизитов оставлен.
- **Минимальный заказ 5 000 ₽ — показ + блокировка**:
  - Константа `MIN_ORDER_AMOUNT = 5000` в `frontend/src/lib/site.ts` и `MIN_ORDER_AMOUNT` в

  - Бэк (защита от обхода): `backend/app/api/v1/endpoints/orders.py` — при `total < MIN_ORDER_AMOUNT`
    → HTTP 422 «Минимальная сумма заказа — 5 000 ₽». Проверено: реальный заказ ниже порога → 422.

**Плитки → ГРУППЫ категорий (мультифильтр) — добавлено после проверки на реальной БД:**
- Реальный каталог = 12 510 товаров, 139 дробных категорий с кодами; единых разделов «Бытовая

## Спринт 1 — Прод перестал виснуть по ночам · 2026-06-21

**Проблема:** каждую ночь фронтенд (Next.js) уходил в `unhealthy`, nginx отдавал 504. Прод —
Ubuntu-сервер `139.100.226.168`, `/opt/internet-shop`, деплой через `git pull && ./deploy.sh`.

**Причина:** серверные `fetch` к backend без таймаута (корневой `layout.tsx` рендерится на КАЖДЫЙ
запрос; ночной обмен МойСклад тормозит backend; под трафиком ботов подвисшие SSR-запросы
накапливаются и вешают Next.js). Docker сам НЕ перезапускает `unhealthy`-контейнер.

**Готово (коммит `0c85990`, задеплоено):**
- `frontend/src/app/layout.tsx` и `frontend/src/lib/api.ts`: `AbortSignal.timeout(8000)` на все
  серверные fetch.
- `docker-compose.prod.yml`: сервис `autoheal` (willfarrell/autoheal) — перезапускает зависший
  контейнер за ~30с. Проверено: после деплоя 8 контейнеров, frontend healthy.
